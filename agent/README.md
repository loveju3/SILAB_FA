# 離線問答 Agent（第二部分）

本機 Qwen3-1.7B（Q4_K_M 量化）＋ llama.cpp，只用 CPU、不連網。核心設計是：**模型決定「查什麼、何時停」，Python 負責「實際查、實際算」。** 最終的數字、清單與引用都直接取自工具結果，模型不能自己寫答案。

## 怎麼跑

先執行 `python3 install.py --with-agent`（見 [docs/setup](../docs/setup/README.md)），完成後直接執行：

```bash
python3 ask.py "B1 動力室有哪些設備？" --trace
python3 ask.py "錯誤碼 E-01 屬於哪一類？"
python3 ask.py "哪位回報人的工單最多？"
python3 patrol.py --trace
```

- 成功時 stdout 輸出 JSON、exit 0。失敗時錯誤只寫到 stderr、exit 2，不輸出假答案。
- `--trace` 把每一步的工具選擇、查詢結果、耗時與 token 用量寫到 stderr。trace 含工單原文，只留本機。
- 每次執行會在本機啟動 `llama-server`，只綁定 `127.0.0.1`，結束時關閉。Windows 用 Job Object 確保 CLI 被中止時，模型程序也會一起結束。
- 已在 Windows 原生與 macOS（Apple Silicon，問答 9.1 秒、巡檢 38.2 秒）實跑。Linux 版 llama.cpp 需要 glibc 2.38 以上；Linux 與 WSL 尚未做端到端驗證。
- 模型與 runtime 的版本和 SHA-256 固定在 `setup.py`。Q4 檔由 bartowski 發布，原始模型是 Qwen，不是 Qwen 官方的量化檔。

## 問答（`ask.py`）

**流程：** 模型每一步輸出一個結構化動作（呼叫哪個工具、帶什麼參數）→ Python 驗證參數並執行 → 把結果交回模型 → 模型決定補查，或用 `finish(result_id)` 指定採用哪一次的結果。

**工具：**

| 工具 | 功能 |
|---|---|
| `get_device` | 依 ID、名稱或型號查單一設備的屬性；查無則回 null |
| `devices_at_location` | 查某個位置有哪些設備；查無則回空清單。若填的是設備名稱，回錯誤並提示改用 `get_device` |
| `list_devices` | 列出全部、關鍵或非關鍵設備 |
| `get_error_code` | 查錯誤碼的類別、意思與型號（大小寫、全半形、分隔符號會先統一）；查無則回 null |
| `query_tickets` | 依時間、回報人、設備、文字條件篩選工單，可計數、找最多的回報人、列工單 ID 或讀最近的原文。時間可用 `day`（某一天，或 `today` 代表快照日）、`last_days`（快照前 N 天）、`since`／`until` |
| `get_ticket_details` | 讀最多 20 張指定工單；問單張工單的原文、回報人或建立時間時，用 `field` 直接回該欄位；工單全部不存在時回 null |
| `ticket_status` | 回答「某設備最近出了什麼狀況」：取快照前 7 天字面匹配的工單（可用 `since` 改期間），用第一部分的方案 A 規則判斷每張的故障類別，answer 回最常見的類別；同分取其中最新一張，7 天內沒有工單就看最新一張，完全沒有工單則回 null。note 列出各類別張數與最新一張的原文摘錄 |

此外，模型在第一步可以輸出 `decline`，表示問題與工廠設備、錯誤碼、工單無關，此時回 `answer: null` 並說明不作答；查過任何工具後就不能再 decline。

**停止條件：**

- 模型主動 `finish`。
- 最多 4 次模型決策。
- 整體 29 秒時限，包含模型載入與關閉。
- 重複同一個查詢會收到錯誤提示；超時、超過步數或引用無效結果時，明確失敗。

**資料規則：**

- 計數一定先掃完整的符合集合，evidence 最多附 20 筆；送給模型看的只是預覽（清單前 20 個、原文前 5 筆），完整答案保留在 Python。
- 日期條件 `since` 含邊界、`until` 不含；可寫完整時間（須帶時區），或只寫 `YYYY-MM-DD`（視為 UTC 當日 00:00）。「今天」固定為快照時間 `2026-10-14T15:10:00Z`，不是電腦日期。同時給多種時間條件時，優先順序為 `day` > `last_days` > `since`／`until`。
- 設備、位置、錯誤碼參數是自由文字，模型照抄題目寫法；工具先統一全半形、大小寫、空白、連字號／底線，並把常見簡體字轉成繁體再比對公開對照表。比對不到就回 null 或空清單，不會改成相似的項目（例如 D13 不會變成 D12）。
- 工具錯誤會說明怎麼修正，例如參數照抄了提示詞範例的 `<佔位符>`、把設備或時間填進回報人欄位、查無回報人時列出相近的完整名稱。
- 工單只讀 `data/tickets.jsonl` 的 ticket_id、created_at、reporter、raw_text 四個欄位；公開資料讀 `devices.json` 與 `error_codes.json`。不讀第一部分的預測檔。唯一例外是 `ticket_status`：它把符合條件的工單原文（四欄）交給 `predict.py --method rules`（方案 A 規則）即時分類，類別是規則判斷，不是標籤，note 會寫明。方案 A 曾觀察 dev，這個工具同樣帶有該來源限制；其他工具不載入方案 A 的規則。沒有用較準的 C-FT（dev category 0.898，A 為 0.849），因為 C-FT 載入要 5～12 秒，CPU 忙碌時曾讓兩題超過 29 秒時限；規則分類 24 張約 0.4 秒。開發時可以用 `--tickets data/history.jsonl`；檔名含 dev 的路徑會被拒絕。這只是防呆，不能取代資料使用規範。

**目前限制：**

- 參數的寫法統一只處理簡繁、大小寫與符號，不處理錯字或代稱。工單原文中的設備比對仍是字面比對，原文寫錯字、簡體或代稱的工單會漏掉；也不做跨工單指涉、語意分類或自由摘要。
- 工具 schema 只保證格式正確，不保證模型選對工具或參數。最新實測中，模型仍會漏填題目給的條件（「今天」「原文寫出」）、照抄範例佔位符，以及在需要兩步查詢的題目只查一步。
- 曾試過把設備、位置、錯誤碼做成 schema 的固定選項（含「不在清單中」），結果 1.7B 會把不存在的對象硬選成相似的項目（D13→D12、二樓機房→B1 動力室），已撤回。
- 工單內容不會被當成指令，但這不是完整的 prompt injection 防護。工具都是唯讀的固定操作，沒有 shell、任意路徑或任意 SQL。

**資料來源說明：** 先前讀過的正式 `schema.md` 裡有 dev 的邊界示例。Agent 沒有用這些示例設計提示詞、工具或評測題，也沒讀 dev 檔，但整段對話不能宣稱完全沒接觸過 dev 相關內容。

## 巡檢（`patrol.py`）

1. **候選：** 原文提到關鍵設備（`critical: true`，比對設備編號、名稱、型號）的快照前工單。沒提到關鍵設備的不納入。
2. **縮選：** 依安全詞種類數、再依時間由新到舊，取最多 30 張，讓模型輸入控制在 8192 context 與 120 秒內。全部 975 張逐批交給模型時，曾超過時限。
3. **安全詞優先：** 含安全詞的工單由程式直接列為 high，排在最前面，不交給模型決定。安全詞取自規格的 urgency 規則，例如漏電、冒煙、短路、觸電。
4. **模型補位：** 剩下的名額由模型從沒有安全詞的候選中挑選、排序，並給出 high、medium 或 low。輸出不合法時最多讓模型修正一次。
5. **引文：** 先去掉郵件簽名，再由程式從原文擷取安全詞附近的片段，模型不能改寫引文。

**為什麼安全詞要由程式決定：** 2026-11-16 用舊版（全部交給模型挑）實跑 tickets，5 張含「漏電」的發電機工單全部落選，模型只挑了最新的 10 張，而且全標 high。

**限制：** 設備錯字與代稱、否定句、同一事件的重複回報（會各佔一個名額）都還沒處理。模型對沒有安全詞的工單，priority 可能給得偏高。沒提到關鍵設備、或在縮選時落選的急件會被漏掉。沒經過人工審查，不能宣稱選出了全部工單中最急的 10 張。

## 評測（`evals/`）

```bash
python3 -m unittest discover -s agent/tests -v
python3 evals/run.py --suite synthetic           # 合成題（預設只跑開發組）
python3 evals/run.py --suite history             # 用 history 出的題
python3 evals/run.py --suite synthetic --split holdout  # 保留組：版本凍結後才跑
python3 evals/run_patrol.py --dataset tickets    # 巡檢格式與時限檢查
```

`evals/run.py --model <GGUF 路徑>` 可換成其他本機模型比較（預設 Qwen3-1.7B Q4_K_M），報告會記錄所用模型。

- **合成題（49 題）：** 13 張人工合成工單加上公開對照表；開發組 44 題，保留組 5 題在版本凍結後以 `--split holdout` 跑一次（2026-11-17 已執行）。題型包含查表、計數、日期邊界、排名同分、未知工單、無關問題拒答、口語問法、相對時間、多步查詢、設備最近狀況、含簡體與錯字的工單，以及設備／位置／錯誤碼的寫法變體（簡體寫法要查得到、相似但不存在的要回空）。每題在 `evals/fixtures.json` 記錄設計理由。
- **history 題（12 題）：** 從 history 的四個輸入欄位計算預期答案，不使用答案標籤；其中 6 題公開查表題與合成題共用。
- **評分方式：** 每題重新啟動 `ask.py` 並載入模型，要求答案值與 JSON 型別完全相符、引用集合完全相符、耗時 ≤ 30 秒。查無資料與無關問題的答案都是 `null`；程序錯誤或逾時不算答對。目前尚未支援的能力照常計入分母。
- **巡檢檢查：** 只驗證格式、引用能對回原文、工單不重複與時限，沒有排序正確率的標準答案。

結果見 [VALIDATION.md](VALIDATION.md)。這些都是開發評測，不能當作隱藏題的成績。Agent 有依合成題開發組與 history 題的失敗回頭修改，所以這兩組分數偏樂觀；保留組在修改期間沒有執行，凍結後只跑一次，作為較獨立的參考。全程沒有讀取 dev。

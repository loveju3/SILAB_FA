## 已知錯誤與開發觀察

- 合成 `reporter-count` 題仍失敗：模型把完整回報人名稱縮成單字，工具精確比對後得到 0。工具本身的完整姓名計數有契約測試，但自然語言到參數的正確性仍有限制。沒有針對這個姓名增加特例。
- 初始模型容易混用位置、設備識別與 single／critical 旗標，設備查詢拆為不同用途工具後改善。文字篩選也曾漏條件，現在明列參數語意、示例並回傳 applied_filters 供模型核對。
- 巡檢曾因模型把多段症狀改寫成非逐字引句而拒絕輸出；一次模型修正仍不足，最終改由程式從選中原文擷取證據，模型負責選單、排序及優先程度。
- 巡檢僅驗證選單／引文契約；是否真正選出全資料最急的工單仍需人審。安全詞與時間的候選篩選可能漏掉其他措辭的急件。
- 尚不支援一般自由文字摘要、所有語意分類、錯字／代稱消解、跨 observation 的新答案組合。工具字面匹配不能冒充語意全集。

## 2026-11-17 設備狀況工具 ticket_status

**問題：** 「D01 最近出了什麼狀況？」原本回 `"B1 動力室"`。沒有任何工具能回答「狀況」，模型只好用 `get_device` 查屬性。

**做法：** 新增 `ticket_status`。answer 定義為快照前 7 天、字面匹配該設備的工單中最常見的故障類別；同分取最新一張，7 天內沒有工單就看最新一張，完全沒有工單則回 `null`。類別由 `predict.py --method rules`（方案 A）即時判斷原文，note 寫明這是規則判斷、不是標籤，並列出各類別張數與最新一張的原文摘錄。提示詞加了路由規則：問狀況用 `ticket_status`，`get_device` 只用在明確問屬性時。這個定義是我們自己的解讀，隱藏題的預期格式不得而知。設計依據為正式規格與合成工單，未使用 dev。

**為什麼不用 C-FT：** C-FT 較準（dev category 0.898，A 為 0.849），但載入要 5～12 秒。在 CPU 被其他程式占用時跑的一輪評測中，有 2 題因此超過 29 秒時限（該輪成績作廢，不列入）。規則分類 24 張約 0.4 秒。另外把工具回傳給模型的內容縮成摘要，不附原文紀錄，省下約 860 個 prompt token，大約 5 秒。

**結果（CPU 空閒時一次完整執行，未挑選重跑）：**

- 開發組 **25/39**。原本 36 題 21→22（`device-ticket-match` 由失敗轉為通過，沒有題目退步）；新增 3 題設備狀況題全部通過（同分取最新、期間內無工單退回最新一張、無工單回 null）。

## 2026-11-17 日期、拒答與寫法變體（凍結版）

**起點：** 當天重跑上一版，開發組 24/39（文件紀錄為 25/39，差一題屬模型輸出的隨機變動）。失敗依原因分為四類：模型自己換算日期寫錯（B）、照抄提示詞範例的值（C）、參數放錯欄位（D）、無關問題或查無資料時沒有回 null（A）。設計依據是正式規格、合成題與 history 題的 trace，未讀取 dev。

**改動：**

- **日期（B）：** `query_tickets` 新增 `day`（某一天，或 `today` 代表快照日）與 `last_days`（快照前 N 天），由程式換算區間，模型不必自己算。`since`／`until` 可只寫 `YYYY-MM-DD`（視為 UTC 00:00）。同時給多種時間條件時依 `day` > `last_days` > `since` 取用，不回錯誤；先前回錯誤時，模型會原樣重送直到步數用完。`ticket_status` 的 `since` 同樣接受只寫日期。
- **範例照抄（C）：** 提示詞範例改用 `<位置>`、`<人名>` 這類佔位符，工具收到含佔位符的參數會回錯誤，要求填題目中的實際值。
- **參數放錯（D）：** 回報人欄位填的是設備、工單編號或時間時，錯誤訊息說明應改填哪個參數；查無回報人時列出相近的完整名稱，否則回 0。`devices_at_location` 收到設備名稱時，提示改用 `get_device`。`get_ticket_details` 新增 `field`，可直接回單張工單的原文、回報人或建立時間。

## 2026-11-17 漏填條件檢查

**發現：** 依 HW_RULES 從乾淨 clone 重測時，用 `tickets.jsonl` 抽測「2026-10-01 之後 D05 有幾張工單？」，回答 911。trace 顯示模型只帶 `since`、漏了設備，數成 10/1 之後的全部工單；原文提到 D05／除濕機／DH-50 的只有 41 張。開發組 `literal-device`、`relative-today-count` 也是同一類錯（漏設備、漏日期）。這次沒有讀取 dev。

**原因有兩層：**

1. 提示詞只有「問<日期>之後有幾張」→ 只帶 `since` 的範例，模型照抄。
2. 被提醒後仍補不上，是因為 llama.cpp 把 JSON schema 轉成輸出文法時，必填欄位排最前，選填欄位只能照 schema 宣告順序出現（`device_id → reporter → day → last_days → since → until → contains_any`）。模型照抄上一次的 `operation, since` 後，文法已不允許再寫 `device_id`，只能把「D05」塞進 `contains_any`，結果只比對原文字串，得到 0。

**改動：** `query_tickets` 執行前，程式比對題目原文：

- 題目提到公開設備的編號、名稱或型號（含簡體），但 `device_id` 沒填它；或題目有明確時間（日期、`10/1`、今天、最近 N 天、本週等，「最近一次」不算），但 `day`／`last_days`／`since`／`until` 都沒填，就不執行，回錯誤。錯誤訊息附一個補好的完整動作，參數**照文法順序排列**，模型可以直接照抄。`contains_any` 不算帶了設備條件。
- 最多提醒 2 次；同一個動作原樣重送就照模型的決定執行。這樣誤判最多多花一步，「查、查、查、finish」仍在 4 步內，不會因此失敗退出。程式不替模型改參數。

**撤回的做法：**

- 只用文字說明「請改填 device_id」：模型三次都照樣放進 `contains_any`（原因見上面第 2 點）。
- 只提醒一次：模型第二次的錯誤寫法（改放 `contains_any`、或補設備時把 `day` 弄丟，回 87）直接被放行。
- 在提示詞加「設備＋日期」組合範例：開發組 `top-reporter` 退步，模型照抄範例佔位符後自行編了人名。temperature 為 0，確定是這行範例造成，已拿掉，只保留程式檢查。

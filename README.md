## 現場狀況與任務目標

工廠現場的師傅跟操作員回報設備故障時，訊息通常長這樣：

```
角落那台,那边□近很热  那台撐不住…
配電盤啟動 0.5 秒有一聲□響
監控主機變頻器散热風扇没转 机殼很燙…
```

錯字、簡體、口語、缺字（甚至像 `□`、`` 這種現場人員貼上噴掉的符號）、沒有標點，都是真實世界的日常！檔案本身是標準 UTF-8，請放寬心把那些特殊符號當成「現場漏打的字」來處理就好，不用擔心是檔案壞掉。

目前這些工單都是靠人工一張張分流，我們希望能打造一個聰明的自動化系統：判斷是哪台設備、屬於哪類故障、急不急、以及是不是重複報修。

線上跑的是一份簡單的關鍵詞比對 baseline（在 `baseline/predict.py`），分數大約只有 0.44，錯得很有規律。你的任務就是帶領系統升級！

## 作業包含兩個部分（第一部分另含 2 GB 記憶體演練，見下；共三批交付：第一部分、2 GB 版本、第二部分）

1. **第一部分：批次分流（Batch Triage）**
   處理 2,000 張工單，幫每張單判斷四個結構化欄位，並加上一句給現場的實用處置建議。
2. **第二部分：智慧問答 Agent（Interactive Agent & Evals）**
   現場人員會用自然語言向系統提問（例如「D01 最近出了什麼狀況？」），你的 Agent 要能調用工具查出答案、給出依據，並且附上你親自設計的評測集來證明它夠準！

_除了 2 GB 那一題需要一個能限制記憶體的環境，其餘不用管部署：不用架 Web API、不用寫 CI/CD，把精力留給演算法、模型與你的工程設計就好！_

## 建議的工作順序

建議可以從 repo 根目錄照著這個節奏玩玩看：

```bash
# 0. 把 baseline 複製成你自己的版本（也可以自己從頭寫）
cp baseline/predict.py predict.py

# 1. 先跑跑看 baseline，看看分數和錯在哪裡
python3 baseline/predict.py data/dev.jsonl baseline_dev.jsonl
python3 baseline/evaluate.py baseline_dev.jsonl data/dev.jsonl

# 2. 開始發揮你的解法！開發時用同一套評分來觀察進展
python3 predict.py data/dev.jsonl dev_predictions.jsonl
python3 baseline/evaluate.py dev_predictions.jsonl data/dev.jsonl

# 3. 完成後，為待分流工單產出最終預測
python3 predict.py data/tickets.jsonl tickets_predictions.jsonl

# 4. 量效能（總時間 + 逐筆 P50／P95／最大值），寫進 bench.md
# 5. 換成 2 GB 上限再跑一次，掉多少分在 dev.jsonl 上量，寫進 budget.md
```

`tickets.jsonl` 沒有提供答案，所以在本機算不出分數是完全正常的喔！

## 運行環境與產品限制

在真實邊緣端或內網運作時，運算資源是有限的，所以我們設定了幾個模擬真實環境的產品條件：

- **時間預算**：平均每筆 ≤ 0.24 秒（2,000 筆在 8 分鐘內跑完，單機 CPU 執行）。
- **離線推論**：推論時不能呼叫外部雲端 API，必須在本機離線跑通（開發時你用什麼雲端工具輔助寫 code 都沒問題）。
- **記憶體友善**：在一般的 8 GB RAM 筆電上能順暢執行。

模型權重不需要放進 Git repo（避免 repo 太大），只要在 README 附上下載指令或安裝步驟即可，確保我們也能在同等環境重現。

### 效能量測方式

**總時間**

- 輸入完整的 `data/tickets.jsonl`，從啟動 `predict.py` 到寫完輸出檔為止量測時間（包含模型載入、推論與寫檔；不含事前安裝，套件與模型權重下載都不算）。總時間 ≤ 480 秒。
- 記錄推論時的峰值記憶體與使用的量測工具。若在 8 GB 機器上驗證最好，若環境不同也請大方註明實際規格與「未在 8 GB 上驗證」即可。

**單筆延遲分佈（這一段請認真做）**

平均值會騙人——999 筆很快、1 筆卡 10 秒，平均還是漂亮的。所以我們要看你量到的是哪一端：

- 逐筆記錄處理時間，報告 **P50 / P95 / 最大值**。
- 說明你**怎麼量的**：量了幾次、有沒有預熱、是否排除模型載入、用什麼工具。
- 如果 P95 明顯高於 P50，請解釋你認為的原因。

**交一份 `bench.md`**，內容包含：量測腳本或指令、上述數字、以及你怎麼確認這些數字可信。也把選型時實測過的每個方案放進同一張表（一個方案一列）；沒實測的只寫「評估後放棄」就好。

## 第一部分：批次分流

針對 `data/tickets.jsonl`，預測出每筆工單的四個結構化欄位以及一句實用處置建議。具體的欄位型別、判斷邊界與計分權重請參考 `schema.md`。

輸出比四個欄位多。每行要有的欄位是：`ticket_id`、四個判斷欄位（`device_id`／`category`／`urgency`／`duplicate_of`）、`llm_used`（JSON 布林）、`suggestion`。**缺 `ticket_id`、四個判斷欄位或 `llm_used`，那一筆會被視為無效預測，四個計分欄位都不給分。缺 `suggestion` 只會被 `evaluate.py` 警告一次，不影響分數。** 完整格式見 `schema.md`。

### 第一部分交付項目

- 放在 repo 根目錄的 `predict.py`，支援指令 `python3 predict.py <輸入.jsonl> <輸出.jsonl>`（可複製 baseline 再改寫）。
- **這個兩參數的呼叫方式請保持可用**。你可以加其他參數（例如 `--mem-limit`），但 `python3 predict.py <輸入> <輸出>` 要能直接跑，我們會用這個形式評分。
- `tickets_predictions.jsonl`：對 `data/tickets.jsonl` 每筆工單的預測結果。其中 `suggestion` 欄位不計分，我們會抽幾筆讀，看建議是否對得上那張單的現象。預算撐不住就別為了它呼叫模型——規則或模板產生的句子也可以，但我們會看你抽樣的那幾句是不是只能套在那一張單上。
- `bench.md` 裡貼上 `dev.jsonl` 四個欄位各自的分數（`evaluate.py` 的輸出）。
- 選型對照表。
- `bench.md`：效能量測。內容請含這五項：① `dev.jsonl` 四個欄位各自的分數（`evaluate.py` 的輸出）② 總時間＋峰值記憶體＋量測指令 ③ 逐筆 P50／P95／最大值＋量測方法（幾次、有無預熱、是否排除載入）④ 每個實測方案一列的延遲／記憶體對照表 ⑤ 你怎麼確認這些數字可信。

### 記憶體預算演練：同一題，2 GB

8 GB 是筆電，不是現場。很多客戶的機器只給得起 2 GB。

請用**同一份 `data/tickets.jsonl`、同樣的 0.24 秒預算**，在 **2 GB 記憶體上限**下再跑一次。不需要重新想解法，但很可能要換模型、換策略、或改流程。

_這一題只針對第一部分。第二部分照原本的 8 GB 條件就好。_

**怎麼限制記憶體**

2 GB 上限可以考慮用 Docker 限制記憶體（例如 `--memory=2g`），做法由你決定。用哪一種、怎麼確認真的有在 2 GB 上限下跑，寫在 `budget.md`。

**交三樣：**

- `predict_2gb.py`（或 `predict.py --mem-limit 2g` 模式，只要能重現即可；前面說的兩參數預設行為不要改掉）
- `tickets_predictions_2gb.jsonl`
- `budget.md`：你改了什麼、**在 `dev.jsonl` 上量四個欄位各掉多少分**、2 GB 版本跑 `tickets.jsonl` 的總時間與 P50／P95（同樣的 0.24 秒預算有沒有守住）、為什麼這樣取捨、有沒有哪一欄你乾脆放棄只回 `null`

_`tickets.jsonl` 沒有答案，所以掉分請拿 `dev.jsonl` 量；`tickets.jsonl` 那一份只要交出輸出檔就好。_

_這一題沒有標準答案。我們看的是你的取捨順序，以及你能不能說清楚「為什麼先砍這個」。_

**三個先講清楚的：**

- `device_id`、`category`、`duplicate_of` 填 `null` 在格式上完全合法（見 `schema.md`），但計分會反映出來。`urgency` 例外，它一定要三選一。所以「放棄某一欄」是可以的，只是你要說明為什麼它最不值得留。

- **2 GB 版本不會拿我們的隱藏測試打分。** 放棄某些欄位是合理的取捨，用同一套分數去罰它會搞錯重點。我們看的是 `budget.md` 有沒有寫齊上面那幾項（改了什麼、dev 上四欄各掉多少、總時間與 P50／P95、為什麼這樣砍），以及能不能重現。

## 第二部分：智慧問答 Agent

在工廠裡，現場主管不會只看報表，他們常會直接問：「D01 空壓機的錯誤碼 E-01 是什麼意思？」、「哪些設備在 B1 動力室？」、「最近哪位師傅報修最多？」
這時候系統就需要像一位可靠的助理，能聽懂問題、主動調用工具去翻工單或查設備資料，然後給出精準解答！

### 兩部分怎麼搭配？

第一部分產出的 `tickets_predictions.jsonl` 是可能有錯的線索，不是標準答案。第二部分可以善用它（例如拿你預測的類別快速篩選），但在最終答題時不能把它當成絕對事實。

### 查詢範圍規範

- 第二部分的事實依據只能是 `data/tickets.jsonl` 的原始內容。`tickets_predictions.jsonl` 可以拿來縮小查詢範圍，但答案、計數與 `evidence` 都以原始工單為準。`dev.jsonl` 與 `history.jsonl` 僅供開發與自測（你的 `evals/` 可以拿它們出題），但 `ask.py` 回答隱藏題時不能把它們當成證據。
- 廠區的 `devices.json` 和 `error_codes.json` 是公共知識，隨時可以查閱。
- 日期一律以 UTC 為準。「2026-10-01 之後」代表 `>= 2026-10-01T00:00:00Z`（含當日 0 點）。資料快照時間為 `2026-10-14T15:10:00Z`，也就是 `data/tickets.jsonl` 的最後一筆，「今天」即以此時間點為準。`dev.jsonl` 的工單時間延伸到 2026-10-16，只供自測用，不要拿它推算「最近幾天」。

### 1. `ask.py`：問答 Agent

```bash
python3 ask.py "D01 空壓機的錯誤碼 E-01 屬於哪一類？"
```

執行後輸出 JSON（單行或格式化多行皆可）：

```json
{
  "answer": "temperature",
  "evidence": [],
  "tools_used": ["get_device", "get_error_code"],
  "note": "進氣溫度過高"
}
```

- `answer`：必須是乾淨的裸值，方便自動化評估：
  | 題目問什麼 | answer 格式範例 | 常見錯法 |
  |---|---|---|
  | 幾張、數量 | `23` | `"23"`、`"共 23 張"` |
  | 哪些清單 | `["D05", "D11"]` | `"D05、D11"` |
  | 名稱或類別 | `"飲水機"`、`"software"` | `"是飲水機"`、`"不確定，可能是飲水機"` |

  答案只放那個值本身，不要加前後文。要補充說明放 `note`。問設備一律回編號（如 `"D05"`）；題目明確問「名稱」才回名稱（如 `"飲水機"`）；問類別回 enum（如 `"software"`）。

  我們會用 14 題隱藏題目跑你的 `ask.py`（見評分方式），**14 題每一題只問一件事**，`answer` 只放那一個值，其他說明一律放 `note`。

- `evidence`：填你引用的 `ticket_id`。查對照表就能回答的給 `[]`；用到工單的題目列 1～20 筆，超過 20 筆就挑代表性的前 20 筆。查過工單但無符合結果（`answer` 為 0 或空陣列）時，`evidence` 給 `[]` 不算錯。**這欄不計分**，但格式不對（超過 20 筆、編號不存在、該列卻空著）該題會判錯。
- `tools_used`：列出呼叫的工具名稱（工具自己設計，命名自訂）。
- `note`（選填）：若有給人看的補充說明可放在這，不影響計分。

### 2. `patrol.py`：主動巡檢

```bash
python3 patrol.py
```

不給任何問題。系統主動掃描 2,000 張待處理工單，挑出以快照時間來看**當下最迫切該處理的 10 張工單**：

```json
[
  {
    "ticket_id": "T02293",
    "reason": "回報人寫「同一个问题」，產線 A 區輸送帶馬達外殼破了",
    "priority": "high"
  }
]
```

`reason` 是展示你產品思維的地方：為什麼優先選這 10 張？理由必須真實反映該工單狀況，請不要引用資料裡不存在的資訊（例如「前兩張已結案」，因為工單資料沒有結案欄位）。`priority` 建議填 `high`／`medium`／`low`（人審為主，不做自動比對）。

### 3. `evals/`：你的專屬評測集

我們相信優秀的 AI 工程師一定具備「為自己的系統設計良好 Evals」的能力！
請準備至少 10 題你自己設計的問答評測（包含問題與預期正確答案）：

附上一支能一鍵跑完評測的腳本，並在簡短報告中聊聊：拿到幾分、錯在哪、哪些題目打破了你原本的預期。

### 第二部分產品條件

- 單一問題回答時間 ≤ 30 秒（含模型載入，每次 `python3 ask.py "..."` 進程啟動到印出 JSON 為止），同樣是單機 CPU、離線。
- `patrol.py` 整體執行時間 ≤ 120 秒。
- 推論過程不能連網，結束碼為 0。除錯或 trace 訊息請走 stderr，不要干擾 stdout 的 JSON 輸出。

### 核心機制：讓模型做決策

這也是這部分被稱為 Agent 的關鍵：**下一步要呼叫哪個工具、什麼時候可以停下來輸出答案，是由模型看完上下文後自己決定的**，而不是程式寫死的流程。

- 模型決定工具與參數，你的程式負責執行工具並將觀察結果（Observation）餵回給模型。
- 請設計好**停止條件**，確保程式穩健結束。
- `ask.py` 請支援 `--trace` 參數，將推理軌跡輸出到 stderr，讓我們能欣賞你的 Agent 是如何思考與決策的！
  面試時我們可能會請你現場展示 trace 喔！

### 第二部分你可以自由決定的事

- 選擇你喜歡且 8 GB 跑得動的小模型。
- 工具切分方式（粗粒度或細粒度都可以，只要有你的設計考量）。
- Prompt 設計、評測集生成方式、以及是否使用 Agent 框架（手刻 while 迴圈或用現成框架皆可）。

## 評分與審查方式

- **第一部分客觀分**：四個欄位計分規則詳見 `schema.md`。我們內部有一份同樣規格但完全未公開的 300 筆測試資料，會用你的 `predict.py` 跑出客觀評分。
